## 1. Назначение и границы

### 1.1. Назначение

Резидентная утилита для Windows, исправляющая текст, набранный в неверной раскладке клавиатуры. По нажатию одной клавиши (по умолчанию `Pause/Break`) последнее набранное слово перекодируется в другую раскладку, а раскладка активного окна переключается на соответствующую.

### 1.2. Ключевой принцип

Программа делает **одну вещь** и делает её технически безупречно. «Лёгкость» понимается как отсутствие постороннего функционала, а не как упрощение инженерной реализации.

### 1.3. Явно вне области (не реализуется)

| Функция | Причина исключения |
|---|---|
| Автоматическое определение неверной раскладки | Требует словарей и эвристик — основной источник ложных срабатываний в аналогах |
| Автозамена, автотекст, аббревиатуры | Посторонний функционал |
| История буфера обмена | Посторонний функционал |
| Транслитерация (кириллица → латиница по звучанию) | Не является задачей исправления раскладки |
| Исправление случайного `CapsLock` (пРИВЕТ → Привет) | Родственная, но иная задача — режим набора, а не раскладка |
| Автообновление, телеметрия, любая сетевая активность сверх чтения ленты автора (FR-102) | Требование безопасности, см. §9, SEC-03 |
| Дневник набранного текста | Категорически запрещено, см. §9 |

## 2. Глоссарий

| Термин | Значение |
|---|---|
| **HKL** | `HKL` — дескриптор раскладки клавиатуры Windows |
| **Нажатие (Stroke)** | Одно событие клавиатуры, сохранённое в буфере: VK, скан-код, модификаторы, HKL, произведённый символ |
| **Буфер набора** | Кольцевой буфер нажатий с момента последнего сброса |
| **Сброс** | Очистка буфера набора при наступлении события границы. Границы двух родов (FR-10): **жёсткая** — сброс наступает немедленно; **мягкая** — сброс отложен, содержимое буфера живёт до первой следующей клавиши, которая в буфер пишет. Мягкая граница ровно одна — пробел |
| **Сессия конвертации** | Серия последовательных нажатий горячей клавиши без промежуточных нажатий других клавиш |
| **Путь буфера** | Основной сценарий: конвертация по буферу набора |
| **Путь выделения** | Дополнительный сценарий: конвертация выделенного текста через буфер обмена |
| **UIPI** | User Interface Privilege Isolation — механизм Windows, запрещающий процессам низкой целостности воздействовать на окна высокой |
| **LL-хук** | Низкоуровневый хук `WH_KEYBOARD_LL` |

## 4. Функциональные требования

### 4.1. Захват ввода

**FR-01.** Программа устанавливает один глобальный хук `WH_KEYBOARD_LL` на выделенном потоке ввода.

**FR-02.** Горячая клавиша перехватывается **внутри хука**, а не через `RegisterHotKey`. Обоснование: хук вызывается синхронно в потоке ввода и гарантирует корректный порядок относительно остальных нажатий, тогда как `WM_HOTKEY` доставляется асинхронно через очередь сообщений, что создаёт гонку.

**FR-03.** Собственный инжектированный ввод фильтруется по магической сигнатуре в поле `dwExtraInfo` структур `INPUT`, сверяемой с `KBDLLHOOKSTRUCT.dwExtraInfo`. Фильтрация по флагу `LLKHF_INJECTED` **запрещена** — она отсекает легитимный сторонний ввод.

**FR-04.** Каждое нажатие сохраняется в буфер в виде структуры:

```rust
#[derive(Clone, Copy)]
struct Stroke {
    vk:    u16,          // виртуальный код
    scan:  u16,          // скан-код
    mods:  u8,           // битовая маска: Shift|Ctrl|Alt|AltGr|Caps|Extended
    hkl:   isize,        // раскладка на момент нажатия
    time:  u32,          // KBDLLHOOKSTRUCT.time — для разрешения гонок
    chars: [u16; 4],     // результат ToUnicodeEx (лигатуры до 4 UTF-16 единиц)
    len:   u8,
}
```

Хранение **скан-кода**, а не только символа — принципиальное решение. Оно обеспечивает: независимость от конкретной пары раскладок, корректную обработку клавиш с разной семантикой в разных раскладках (`Shift+2` = `@` в EN и `"` в RU), а также идеальную точность при циклическом переборе трёх и более раскладок (§4.4).

**FR-05.** Флаг `LLKHF_EXTENDED` сохраняется в `mods` и восстанавливается при повторной инжекции.

**FR-06.** Декодирование символа выполняется через `ToUnicodeEx` с обязательным флагом `wFlags = 0x4` («не изменять состояние клавиатуры»). Без этого флага вызов мутирует внутреннее состояние мёртвых клавиш раскладки и ломает композицию символов в приложении пользователя.

**FR-07.** Ёмкость кольцевого буфера — 256 нажатий, при переполнении вытесняются старые.

**FR-08.** Автоповтор горячей клавиши подавляется: программа отслеживает собственное состояние down/up и реагирует только на первое нажатие до отпускания.

### 4.2. Сброс буфера

**FR-10.** Буфер сбрасывается при наступлении любого из событий. Границы слова двух родов: **жёсткие** — сброс наступает немедленно, и таких границ все, кроме одной; **мягкая** — она ровно одна, пробел, и сброс по ней отложен (проза под таблицей).

| Событие | Источник | Действие |
|---|---|---|
| `Tab`, `Enter`, `Esc` | LL-хук | полный сброс (жёсткая граница) |
| `Space` | LL-хук | мягкая граница: отложенный сброс, проза под таблицей |
| `Backspace` | LL-хук | извлечение одного элемента (не сброс) |
| `Delete`, стрелки, `Home`/`End`/`PgUp`/`PgDn`, `Insert` | LL-хук | полный сброс |
| `Ctrl`/`Alt`/`Win` + клавиша, **кроме комбинаций смены раскладки, названных FR-11** | LL-хук | полный сброс (команда, а не текст) |
| Штрих, не давший символа **ни в одной раскладке кэша FR-20** и не имеющий роли в этой таблице: `F1`…`F24`, `PrintScreen`, `NumLock`, `ScrollLock`, `Application`, браузерные (`VK_BROWSER_*`), пусковые (`VK_LAUNCH_*`), `VK_CLEAR`, `VK_PACKET` | LL-хук | полный сброс |
| Клавиши громкости и медиа, семь: `VK_VOLUME_MUTE`, `VK_VOLUME_DOWN`, `VK_VOLUME_UP`, `VK_MEDIA_NEXT_TRACK`, `VK_MEDIA_PREV_TRACK`, `VK_MEDIA_STOP`, `VK_MEDIA_PLAY_PAUSE` | LL-хук | не пишутся и не сбрасывают |
| Нажатие любой кнопки мыши | Raw Input | полный сброс |
| Смена активного окна | `EVENT_SYSTEM_FOREGROUND` | полный сброс |
| Смена фокуса внутри окна | `EVENT_OBJECT_FOCUS` | полный сброс, **кроме события, вызванного набором (FR-14)** |
| Блокировка сессии, смена пользователя | `WM_WTSSESSION_CHANGE` | полный сброс + обнуление памяти |
| Приостановка программы пользователем | трей | полный сброс + обнуление памяти |
| Любая клавиша после конвертации | LL-хук | полный сброс (завершение сессии конвертации) |

**Мягкая граница — пробел.** Слово кончается пробелом чаще, чем чем-либо другим, и неверная раскладка замечается ровно тогда — когда слово уже отделено. Поэтому пробел слово завершает, но буфер **не сбрасывает немедленно**:

1. Штрих пробела записывается в кольцо как обычный штрих, и буфер переходит в состояние «слово + хвост».
2. Последующие пробелы копятся в хвост: «слово + N пробелов».
3. Первая следующая клавиша, которая в буфер пишет и пробелом не является (буква, цифра, символ), **сначала** сбрасывает старое содержимое — полный сброс с обнулением памяти, как всякий сброс, — и **затем** записывается первым штрихом нового слова.

Пока буфер стоит в этом состоянии, горячая клавиша конвертирует **всё** его содержимое: слово перекодируется, хвостовые пробелы переносятся как есть (пробел — обычный штрих, и в целевой раскладке та же физическая клавиша даёт пробел), раскладка переключается — полный порядок FR-40. Побитовый откат FR-32 работает с хвостом наравне со словом: повторное нажатие возвращает исходное слово с теми же пробелами.

Хвост живёт в том же кольце FR-07 и отдельного предела не имеет; переполнение — по общему правилу кольца. Пустой буфер мягкой границы не знает: пробел, нажатый когда в кольце ничего нет, сбрасывать нечего и состояния «слово + хвост» не открывает.

Мягкость касается ровно одной клавиши. `Tab`, `Enter`, `Esc` остаются жёсткими намеренно: после `Enter` текст часто уже отправлен, а `Tab` уводит фокус, и сброс по смене фокуса съел бы буфер раньше любой мягкости. Жёсткими остаются и все прочие строки таблицы — клик, смена окна, смена фокуса, блокировка сессии, приостановка, клавиша после конвертации, — а пробел с командным модификатором остаётся строкой команды (`Win`+`Space` — исключение FR-11).

**Штрих, который нигде не пишет, — граница.** Правило заменяет список клавиш вопросом: написал ли этот штрих хоть что-нибудь. Клавиша, не давшая символа и не имеющая в таблице роли, действие, а не текст: `F5` перезагружает страницу, `F2` переименовывает файл, браузерная «назад» уводит с неё, а `Application` открывает то же меню, что правый щелчок мыши, — который таблица сбрасывает строкой выше. Список клавиш пришлось бы вести вечно и он был бы неполон на следующей клавиатуре.

Критерий берётся **по всем раскладкам кэша FR-20, а не по текущей**. Клавиша, пустая в раскладке, в которой пользователь набирает, и значащая в той, в которой он думал, что набирает, — это ровно тот штрих, ради которого существуют FR-22 и FR-23: конвертация идёт по скан-коду, и такой штрих переносится в целевую раскладку. Сбрасывать его значило бы противоречить FR-23 с обратной стороны.

**Мёртвая клавиша FR-24 под «пусто» не подпадает.** `ToUnicodeEx` отвечает на неё отрицательным числом и самим мёртвым знаком: штрих несёт символ и метку, и записывается как обычно. «Не дал символа» и «не есть текст» — разные вопросы, и правило задаёт второй.

**Пока кэш FR-20 не построен, правило не применяется.** Критерий тогда не вычислим — спрашивать некого, — а «не знаю» не есть «пусто»: штрихи первых мгновений сессии записываются, как записывались.

**`VK_PACKET` сбрасывает всегда и без обращения к кэшу.** Это не клавиша, а способ, которым система сообщает о чужом `KEYEVENTF_UNICODE`: менеджер паролей заполнил поле, второй переключатель заменил слово, скрипт развернул сокращение. Текст на экране изменился знаками, которые программа декодировать не может, и содержимое кольца перестало описывать поле. Кроме того, в таком событии `wScan` несёт **кодовую единицу знака**, а не скан-код, и чтение её как скан-кода даёт случайные попадания. Собственная замена FR-22 приходит тем же `VK_PACKET` и до буфера не доходит по сигнатуре FR-03.

**Семь клавиш громкости и медиа — не письмо и не команда над текстом.** Они ничего не меняют на экране и не двигают каретку, поэтому слово, которое пользователь набирает, их переживает: не пишутся, не сбрасывают, состояние модификаторов не трогают. Список закрыт семью кодами; браузерные и пусковые клавиши в него намеренно не входят — они запускают приложение или уводят страницу, то есть являются границей в том же смысле, в каком ею является правый щелчок.

**FR-11.** Смена раскладки самим пользователем **не сбрасывает** буфер: HKL хранится по каждому нажатию отдельно. Покрываются все переключатели, которые предлагает системный диалог языковых параметров:

* переход на следующую раскладку — `Alt+Shift`, `Ctrl+Shift`, `Win+Space`;
* переход **на конкретный язык** — (`Ctrl` **либо** `Alt`, любой стороны) + `Shift` любой стороны + клавиша: цифра **верхнего ряда** `0`…`9` либо гравис.

Комбинация ничего не пишет в буфер, ничего из него не удаляет, не трогает счётчик позиции FR-32 и **не закрывает сессию конвертации**: переключение после конвертации сохраняет откат FR-33 (последняя строка таблицы FR-10 к нему не применяется).

`Ctrl` вместе с `Alt` — это `AltGr`, символьный модификатор FR-20, а не переключатель: диалог назначает один модификатор либо другой, но не оба. Цифры дополнительной клавиатуры не входят — это другие физические клавиши, и диалог их не назначает. Без `Shift` `Ctrl`+цифра и `Alt`+цифра остаются обычными командами приложения и сбрасывают буфер. Гравис **без модификаторов** переключателем не считается — см. §10.

HKL служит записью о наборе; направление конвертации всего буфера берётся из HKL **первого** нажатия (FR-26).

**FR-12. Разрешение гонки асинхронных событий сброса.** События Raw Input и `WinEvent` доставляются асинхронно, тогда как хук клавиатуры вызывается синхронно. Возможна ситуация, когда событие клика обрабатывается уже после попадания в буфер последующего символа. Каждое событие сброса несёт временну́ю метку (`GetMessageTime` / `dwmsEventTime`); при обработке события сброса с меткой `T` из буфера удаляются все нажатия с `time <= T`. Полная очистка выполняется только если метка события новее всех нажатий в буфере.

**FR-13.** Для отслеживания кликов мыши используется **Raw Input** (`RegisterRawInputDevices` с флагом `RIDEV_INPUTSINK`, доставка через `WM_INPUT`), а не `WH_MOUSE_LL`. Обоснование: `WH_MOUSE_LL` вызывается на каждое перемещение курсора и помещает процесс в системный критический путь ввода мыши; Raw Input доставляется асинхронно в собственную очередь сообщений и не влияет на отзывчивость системы.

**FR-14. Событие фокуса, вызванное набором.** Приложения поднимают `EVENT_OBJECT_FOCUS` не только при переходе пользователя в другое поле, но и в ответ на сам набор: раскрытие списка подсказок и смена выбранной подсказки (адресная строка Chromium/Edge объявляет выбранную строку списка активным потомком поля, и MSAA отдаёт это как `EVENT_OBJECT_FOCUS` с другим `idChild` того же окна), автодополнение, эхо Electron. Событие `EVENT_OBJECT_FOCUS` переднего окна с меткой времени `T`, для которого в буфере есть штрих либо запомненное стирание `Backspace` с меткой `t`, `T − Δ < t ≤ T`, при отсутствии между `t` и `T` границ иного рода таблицы FR-10, считается реакцией приложения на набор: буфер **не сбрасывается**, запись **не приостанавливается**. Δ = 1500 мс. Проверка поля пароля FR-71/FR-72 для такого события запускается как обычно; вердикт «поле пароля» обнуляет буфер и выключает запись по получении (FR-70). Правило действует, только пока запись разрешена (`Ordinary`, `Undetermined`); в состояниях `Pending` и `Password` событие обрабатывается по общему порядку. Смена активного окна (`EVENT_SYSTEM_FOREGROUND`) правилу не подчиняется никогда. Обоснование измерением 2026-09-09 (Edge, адресная строка): первые буквы слова терялись при каждом раскрытии списка подсказок — «нфтвучюкг» → «нфndex.ru».

**FR-15. Таймаут покоя буфера.** Если кольцо непусто и с момента последней правки кольца (запись штриха либо извлечение по `Backspace` — тот же момент, которым пользуется FR-14) прошло не меньше `[buffer] idle_timeout_s`, буфер сбрасывается полностью, как всякий сброс таблицы FR-10: обнуление памяти (SEC-02), обнуление счётчика позиции FR-32 (FR-34), конец сессии конвертации. Откат FR-33 после этого невозможен — это принято. Сброс **тихий**: звука FR-100 нет, пользователя за клавиатурой нет.

Умолчание `300` секунд, `0` выключает правило, потолки при публикации — `30`…`86 400` секунд; `0` остаётся `0`. Файл правится рукой и может содержать что угодно: значение вне потолков не отвергается и не переписывается, а публикуется приведённым к границе.

**Механизм.** Проверка выполняется на такте живости FR-80 (30 с, поток ввода) и больше нигде. Собственного таймера у правила нет, и в callback хука не добавляется ничего. Отсюда и нижний потолок: срок короче такта соблюсти нечем, и написавший `5` получил бы тридцать секунд, думая, что получил пять. **Точность:** сброс не раньше `idle_timeout_s` и не позже `idle_timeout_s + 30 с`. После сна машины сбрасывает первый такт после пробуждения, если возраст вышел, — это желаемое поведение.

Сравнение времени — по правилу FR-12: часы 32-разрядные и переполняются раз в 49 суток 17 часов, но возраст считается по модулю 2³², поэтому переполнение не особый случай — слово, набранное перед ним, доживает свой срок и на той стороне нуля. Запаркованный буфер (FR-70) пуст — сбрасывать нечего.

**Обоснование.** Набранное слово живёт до ближайшей границы FR-10, а границы может не быть часами: пользователь набрал полстроки, его отвлекли, и штрихи стоят в памяти процесса до конца дня (SEC-01). Второе основание арифметическое: разрешение гонок FR-12 опирается на посылку «штрих в буфере старше нескольких минут не бывает», и до этого требования её ничто не обеспечивало.

### 4.3. Движок перекодировки

**FR-20.** При старте строится кэш соответствий: перебор VK `0x08..0xFF` × восемь комбинаций модификаторов (—, Shift, Caps, Shift+Caps, AltGr, AltGr+Shift, AltGr+Caps, AltGr+Shift+Caps) × все установленные HKL (`GetKeyboardLayoutList`). Для каждой комбинации вызывается `ToUnicodeEx`. Результат — двусторонние отображения «скан-код + модификаторы ↔ символ» для каждой раскладки.

**FR-21.** Кэш перестраивается, когда меняется состав раскладок сеанса. `WM_INPUTLANGCHANGE` до программы не доходит — Windows шлёт его окну с клавиатурным фокусом, а это окно другой программы, — поэтому поток ввода сам сверяет список `GetKeyboardLayoutList` со списком кэша по собственному зонду. Зонд посылают поток наблюдения — при смене окна и фокуса и при возвращении сеанса (разблокировка, пробуждение) — и хук при отпускании модификатора. Кэш перестраивается, если раскладка добавлена, удалена или переставлена; смена одной лишь активной раскладки обновляет штамп FR-04 и кэша не трогает. `WM_DEVICECHANGE` (подключение и отключение клавиатуры) перестраивает кэш безусловно.

**FR-22.** Конвертация пути буфера: для каждого сохранённого нажатия берётся его скан-код и маска модификаторов, и запрашивается символ, который эта же физическая клавиша производит в **целевой** раскладке. Символьные таблицы соответствия не используются.

**FR-23.** Если для нажатия нет отображения в целевой раскладке, исходный символ сохраняется без изменений. Конвертация не прерывается.

**FR-24.** Мёртвые клавиши: отрицательный результат `ToUnicodeEx` означает мёртвую клавишу. Такое нажатие сохраняется в буфере с флагом и при конвертации переносится без изменений. Для пары RU/EN мёртвые клавиши отсутствуют; требование обеспечивает корректность при добавлении иных раскладок.

**FR-25.** Аварийный резерв: жёстко зашитая таблица RU↔EN, используемая только при сбое построения динамического кэша.

**FR-26.** Направление конвертации пути буфера определяется HKL, записанным при **первом нажатии буфера**, и настройками раскладок (§4.4). Анализ содержимого текста не применяется.

### 4.4. Выбор целевой раскладки

**FR-30. Режим «Пара» (по умолчанию).**
- Если в системе установлены ровно две раскладки — работа полностью автоматическая, настройка не требуется: целевая раскладка есть вторая из двух.
- Если установлено три и более, а режим оставлен «Пара» — пользователь явно задаёт рабочую пару «источник ↔ цель». Остальные раскладки игнорируются. Поля предзаполняются первыми двумя раскладками системного списка.

**FR-31. Режим «Несколько раскладок».** Включается пользователем вручную. Горячая клавиша циклически перебирает раскладки из настраиваемого упорядоченного списка: первое нажатие — вариант 2, второе — вариант 3, и так далее по кругу с возвратом к исходному варианту.

**FR-32. Точность цикла.** Буфер хранит **исходные нажатия неизменными**; рядом ведётся счётчик позиции в цикле. Каждое нажатие горячей клавиши рендерит оригинальные скан-коды в очередной раскладке. Замена содержимого буфера перекодированным текстом **запрещена** — она приводит к накоплению искажений при многократных проходах. Возврат к началу цикла восстанавливает исходный текст побитово точно.

**Примечание к FR-32.** Побитовая точность относится к буферу нажатий, а не к экранному тексту: инжекция (`KEYEVENTF_UNICODE`) не выполняет композицию мёртвых клавиш, поэтому возврат отрисовывает штрихи раздельно — набранное `café` возвращается как `caf'e` (измерено этапом Э20, 2026-08-31). Текст остаётся читаемым и правится рукой; для раскладок без мёртвых клавиш (пара RU/EN) обещание точно буквально. Побитовая точность относится к буферу, набранному в одной раскладке. Буфер, в середине которого раскладка сменилась (FR-11), рендерится целиком из раскладки первого нажатия: для смешанного буфера возврат к началу цикла исходного текста не восстанавливает — §10.

**FR-33.** В режиме «Пара» механизм тот же при длине цикла 2, благодаря чему повторное нажатие горячей клавиши работает как откат без отдельной реализации.

**FR-34.** Счётчик позиции в цикле сбрасывается вместе с буфером.

**FR-35.** Раскладки на базе TSF/IME (китайская, японская, корейская) исключаются из списка участвующих и не предлагаются в настройках. Обоснование: композиция символов в IME разрывает соответствие между нажатиями и содержимым поля ввода.

### 4.5. Замена текста

**FR-40.** Порядок операций при срабатывании:

1. Подавить горячую клавишу (возврат `1` из хука).
2. Поставить задачу в очередь сообщений собственного окна и **немедленно вернуться из хука**. Вызов `SendInput` изнутри хука запрещён — это ре-энтрантность и путь к взаимоблокировке.
3. Снять удерживаемые модификаторы (`Shift`, `Ctrl`, `Alt`, `Win`) явными событиями отпускания.
4. Выполнить замену текста (FR-41).
5. Переключить раскладку активного окна (§4.6) — **только если пакет замены принят системой целиком** (FR-45): при заблокированной инжекции раскладка не трогается.
6. **По возможности** восстановить модификаторы, удерживаемые физически: асинхронный опрос не отличает собственное событие программы от чужого (§10).

**Шаг 3 обязателен**: без него удерживаемый в момент нажатия `Shift` превращает инжектированный ввод в комбинацию с модификатором. Шаг 6 выполняется по возможности (§10).

**FR-41.** Замена выполняется одним вызовом `SendInput` с массивом событий (атомарность и гарантия порядка):
- `N` × (`Backspace` down + up), где `N` — число символов, стоящих на экране;
- перекодированные символы через `KEYEVENTF_UNICODE` (`wVk = 0`, `wScan = символ`).

Символ вне BMP — две кодовые единицы суррогатной пары, каждая как пара down + up, итого **четыре** структуры `INPUT`, все в одном вызове `SendInput`.

**FR-42. Режим совместимости.** Настраиваемая альтернатива: вместо `N` × `Backspace` выполняется `N` × `Shift+Left` с последующей вставкой, при которой выделение заменяется одним событием. Обоснование: в приложениях с автодополнением и автозаменой (IDE, поля браузера с подсказками, Word) одно нажатие `Backspace` может удалить не один символ, а весь подставленный токен.

**FR-42а. Автоматический выбор метода.** Значение `method = "auto"` (умолчание) выбирает метод замены по классу переднего окна в момент замены: консольные окна (`ConsoleWindowClass`, `CASCADIA_HOSTING_WINDOW_CLASS`) получают путь `Backspace`, все прочие — путь FR-42. Обоснование измерением: консольный COOKED-ввод не интерпретирует `Shift+Left` как выделение, и путь FR-42 в нём приписывает замену к неудалённому тексту; путь `Backspace`, в свою очередь, в обычных окнах редактирования подвержен гонке с обработкой стирания приложением при повторных нажатиях. Ни один из двух методов не универсален; выбор по классу окна покрывает оба измеренных случая. Явные значения `backspace` и `selection` остаются ручным принуждением без автоматики. Определение класса выполняется одним вызовом `GetClassNameW` на потоке интерфейса в момент замены и не затрагивает путь хука.

**Примечание к FR-42 и FR-42а.** Метод замены настраивается **только в файле конфигурации** (`[replacement] method`, §7): с 2026-09-01 диалог FR-92 его не показывает — решение пользователя, вопрос 81. Умолчание `auto` выбрано измерением и подходит подавляющему большинству случаев; `backspace` и `selection` остаются аварийным рычагом совместимости для того, кто знает, зачем он его берёт.

**FR-43.** Замена выполняется **до** переключения раскладки. `KEYEVENTF_UNICODE` доставляет символ буквально, минуя раскладку, поэтому гонка отсутствует.

**FR-44.** Настраиваемая задержка между событиями `SendInput` (по умолчанию `0` мс) для приложений, теряющих события при пакетной отправке. Настройка задаётся **только в файле конфигурации** (`[replacement] inter_event_delay_ms`, §7): с 2026-09-01 диалог FR-92 её не показывает — решение пользователя, вопрос 81.

**FR-45.** Возвращаемое значение `SendInput` проверяется. Расхождение с числом отправленных событий фиксируется в диагностическом журнале (SEC-07, модуль `diag`).

### 4.6. Переключение раскладки

**FR-50.** Переключение выполняется одним способом: `PostMessage(hwndForeground, WM_INPUTLANGCHANGEREQUEST, 0, hkl)`. Вердикт — перечитывание раскладки потока фокуса по FR-52, а не возвращаемое значение вызова.

Прежняя редакция предписывала цепочку из трёх способов с переходом к следующему при неуспехе (2 — `AttachThreadInput` к потоку активного окна + `ActivateKeyboardLayout` + `DetachThreadInput`; 3 — `ITfInputProcessorProfileMgr::ActivateProfile`, TSF). Цепочка упразднена решением пользователя 2026-08-25 (вопрос 63) по двум измерениям — Т-13-10 (304 круга) и Т-14-2 (300 кругов: консольный хост и окно без цикла сообщений): запасные способы не спасли ни одного круга из 504 исполнений (способ 2 — 0 из 228, способ 3 — 0 из 276); после способа 2 переключается раскладка **вызывающего** потока, а не окна; там, где способ 1 бессилен — окно, не обрабатывающее сообщения, — бессильны все три; способ 2 на таком окне блокирует вызывающий поток неограниченно (60 из 60), что для потока ввода с LL-хуком означает молчаливое снятие хука системой (FR-80).

**FR-51.** Учитывается системная настройка Windows 11 «Позволить выбрать метод ввода для каждого окна приложения» (включена по умолчанию), определяющая область действия переключения.

**FR-52.** Текущая раскладка определяется у потока, которому принадлежит **окно с фокусом клавиатуры**: `GetGUIThreadInfo` для потока переднего окна даёт `hwndFocus`, и раскладка читается `GetKeyboardLayout` для потока этого окна. Если фокусное окно недоступно — `GetGUIThreadInfo` отказал или `hwndFocus` пуст, — используется поток переднего окна, то есть прежнее поведение.

**Основание — измерение T-10-19** (`reviews\T-10-19.md`, 660 кругов, три приложения): раскладка в Windows хранится **по потоку**, и у упакованных приложений Windows 11 верхнее окно переднего плана и окно ввода принадлежат **разным потокам одного процесса**. В упакованном Блокноте они не совпали **ни разу из 220**, а после переключения раскладки сочетанием клавиш, затрагивающего только фокусный поток, раскладка переднего потока расходилась с фактически печатаемой **120 раз из 120 и держалась все 2000 мс наблюдения**. Раскладка потока фокуса не разошлась с фактической **ни разу из 660**. В классических окнах (собственное окно стенда, Chrome) оба потока совпадают всегда, и прежняя формулировка была для них верна.

**Дополнение по измерению Т-14-2** (вопрос 63): у классических консольных окон (`ConsoleWindowClass`) идентификатор потока от `GetWindowThreadProcessId` не принадлежит ни одному потоку с очередью ввода — `GetGUIThreadInfo` отвечает отказом «Параметр задан неверно» (120 из 120), чтение раскладки даёт 0, хотя переключение способом FR-50 фактически состоялось (60 из 60 по независимой проверке). Вердикт по FR-52 в таких окнах невыносим: переключение считается отправленным без подтверждения, ожидания подтверждения не выполняются.

### 4.7. Путь выделения

**FR-60.** Правило выбора источника данных:

> **есть выделение → конвертируется выделение; выделения нет → конвертируется буфер набора**

Одна клавиша, один смысл, два источника данных.

**FR-61.** Алгоритм:
1. Сохранить содержимое буфера обмена (снимок всех доступных форматов, см. FR-64).
2. Отправить `Ctrl+C`.
3. Дождаться изменения `GetClipboardSequenceNumber` с таймаутом (по умолчанию 300 мс). При отсутствии изменения — выделения нет, переход к пути буфера.
4. Прочитать `CF_UNICODETEXT`.
5. Разбить текст на слова — максимальные последовательности знаков без пробельных и управляющих; разделители переносятся без изменений. Для **каждого слова** определить письменность отдельно (строгий максимум различающих знаков среди раскладок-участниц) и перекодировать его в **следующую по циклу §4.4** раскладку относительно его собственного источника: обратное отображение «символ → скан-код» по раскладке источника, затем прямое в целевую. Слово без различающих знаков (цифры, знаки препинания) следует решению по всему тексту; решение по всему тексту при равенстве — раскладка переднего окна. Слово, источник которого не участвует в цикле, переносится без изменений. Это единственное место, где применяется анализ содержимого — скан-коды здесь недоступны. Основание 2026-09-09: предложение из слов в двух раскладках («… ckjdj нфтвуч yj …») конвертировалось одним направлением, и слово другой раскладки оставалось как было. Знак, который в раскладке источника даёт клавиша десятичного разделителя цифрового блока (скан-код `0x53`, без модификаторов), стоящий между двумя цифрами `0`…`9`, восстанавливается как эта клавиша, а не как клавиша основного ряда с тем же знаком: «5,1» ↔ «5.1»; вне цифр — прежнее правило (основание 2026-09-25, вопрос 146: «афиду 5,1» с запятой цифрового блока давало «fable 5?1» — запятая «Русской» восстанавливалась как `Shift` + «/?», а это «?» в английской).
6. Записать результат в буфер обмена, отправить `Ctrl+V`.
7. Переключить раскладку — на целевую раскладку **решения по всему тексту**.
8. Восстановить исходное содержимое буфера обмена с задержкой (по умолчанию 200 мс).

**Примечание к шагу 8.** Восстановление пропускается, если после записи результата программой буфер обмена изменил другой процесс (сверка `GetClipboardSequenceNumber` с меткой собственной записи): затирать новую копию пользователя снимком недопустимо.

**FR-62.** Все обращения к буферу обмена выполняются с повторами: `OpenClipboard` завершается неуспехом, если буфер удерживает другой процесс. Число повторов — 10, интервал — 20 мс.

**FR-63.** Изменения буфера обмена отслеживаются через `AddClipboardFormatListener`.

**FR-64.** Сохранение и восстановление буфера обмена охватывает все перечисленные форматы суммарным объёмом до 4 МБ. При превышении лимита сохраняется только `CF_UNICODETEXT`, факт фиксируется в журнале. Ограничение документируется для пользователя.

**Примечание к FR-64.** Чтение выделения на шаге 4 ограничено тем же потолком 4 МБ: выделение большего размера рассматривается как отсутствие текста, снимок восстанавливается по правилам шага 8. Потолок — один и тот же на снимок и на чтение.

**FR-65.** Путь выделения отключается настройкой. При отключении горячая клавиша работает только по буферу набора.

**Примечание к §4.7 (два тайминга).** Таймаут ожидания буфера обмена шага 3 и задержка восстановления шага 8 задаются **только в файле конфигурации** (`[selection] clipboard_timeout_ms` и `clipboard_restore_delay_ms`, §7): с 2026-09-01 диалог FR-92 их не показывает — решение пользователя, вопрос 81. Потолки задачи T-13-13 действуют по-прежнему и клампят значение при публикации, что тем важнее, что руками в файл можно написать любое число.

**Примечание к §4.7.** В консольных окнах (классы FR-42а) путь выделения не применяется: зонд `Ctrl+C` без выделения является прерыванием и способен убить выполняющийся процесс (измерено T-10-0c). Горячая клавиша при пустом буфере набора в консоли не производит действий.

### 4.8. Защита ввода паролей

**FR-70.** В поле ввода пароля буфер набора **не ведётся**.

**FR-71.** Определение выполняется **асинхронно при смене фокуса, при старте программы и при возврате на рабочий стол пользователя** (после запроса UAC, `Ctrl+Alt+Del`, разблокировки), результат кэшируется в атомарный флаг, который хук читает одной операцией. Вызовы UI Automation межпроцессные и занимают десятки миллисекунд — их выполнение внутри хука категорически запрещено.

**FR-72.** Порядок проверок:
1. Имя процесса активного окна в списке системных окон учётных данных (`LogonUI.exe`, `CredentialUIBroker.exe`, `consent.exe`) → буферизация отключена.
2. Класс сфокусированного элемента `Edit` → `SendMessageTimeout(EM_GETPASSWORDCHAR)` с таймаутом 50 мс; ненулевой результат → буферизация отключена.
3. UI Automation: `IsPasswordProperty` сфокусированного элемента → истина → буферизация отключена.

**FR-73.** Поведение по умолчанию при невозможности определить тип поля (таймаут, неизвестный элемент управления) — буферизация **включена**. Обоснование: отказ от буферизации по умолчанию сделал бы программу неработоспособной в большинстве полей на базе Electron и веб-технологий, где UI Automation отвечает медленно.

### 4.9. Устойчивость

**FR-80. Сторож хука.** Система снимает низкоуровневый хук **молча, без уведомления** в следующих случаях: превышение `LowLevelHooksTimeout` (`HKCU\Control Panel\Desktop`, по умолчанию ~5 с), переключение на защищённый рабочий стол (запрос UAC, `Ctrl+Alt+Del`), смена сессии, выход из режима сна.

Требуется механизм восстановления:
- подписка на `EVENT_SYSTEM_DESKTOPSWITCH`;
- подписка на `WM_WTSSESSION_CHANGE` (регистрация через `WTSRegisterSessionNotification`);
- подписка на `WM_POWERBROADCAST` (`PBT_APMRESUMEAUTOMATIC`);
- периодическая проверка живости хука с интервалом 30 с и переустановкой при обнаружении снятия.

**FR-81. Восстановление иконки в трее.** При перезапуске проводника иконка исчезает. Требуется обработка сообщения, полученного через `RegisterWindowMessage("TaskbarCreated")`, с повторным добавлением иконки.

**FR-82. Единственный экземпляр.** Именованный мьютекс в пространстве `Local\` (один экземпляр на сессию пользователя). При обнаружении работающего экземпляра — вывод уведомления и завершение. ⚠ Примечание (вопрос 84, решение 2): **в отладочной конфигурации при заданной `LANGSW_DEBUG_TIMEOUT_SEC` уведомление подавляется** — вместо модального окна пишется строка журнала §6.2, процесс завершается сразу и с тем же кодом. Ради стендов: модальное окно блокирует процесс, перед которым никого нет, а срок FR-97 второму экземпляру не помогает — он до него не доходит. В поставляемой конфигурации переменной не существует и поведение FR-82 не меняется ни в чём.

**FR-83. Корректное завершение.** Обработка `WM_QUERYENDSESSION` / `WM_ENDSESSION`: снятие хуков, удаление иконки, обнуление буфера, сохранение конфигурации, освобождение мьютекса.

**FR-84. Список исключений.** Настраиваемый список имён процессов, в которых буферизация не ведётся (по умолчанию пуст). Назначение: игры с системами защиты от читерства и приложения, использующие Raw Input в обход стандартного ввода. **В исключённом процессе горячая клавиша не подавляется и достаётся приложению**: нажатие и отпускание проходят нетронутыми, конвертация не запускается, звука FR-100 нет. Отпускание повторяет судьбу нажатия — пропущено нажатие, пропущено и отпускание, даже если вердикт исключения за это время сменился, — потому что приложение обязано увидеть либо целый штрих, либо ни одного. Автоповтор FR-08 при пропуске проходит естественно.

**Примечание к FR-92 (состав разделов).** Разделов шесть, и до 2026-09-01 их было семь. По решению пользователя (вопросы 81 и 82) из окна ушли метод замены FR-42/FR-42а и три миллисекундные настройки — задержка FR-44 и оба тайминга §4.7; раздел «Замена» ушёл вместе с ними, а раздел «Выделение», оставшийся из одной галки, распущен: галка перечислена в «Общих» к сёстрам. **Сами настройки не удалены**: они живут в `config.toml` (§7), правятся руками, читаются `publish_configuration` и клампятся своими потолками — у каждой стоит примечание об этом при её собственном требовании. Строки раздела «Состояние» заполняются при открытии окна и по нажатию «Применить»; пока окно открыто, числа не обновляются.

**Примечание к FR-92 (строки выбора раскладок).** Раскладка называется в списках и комбо своим языковым именем от системы, без идентификатора. Идентификатор — тот самый, какой хранит §7, — приписывается через « — » **только при совпадении имён** и сразу **всем** столкнувшимся строкам: две раскладки одного языка иначе неразличимы. Раскладке, которую система не называет, показывается один идентификатор. Решение пользователя (вопрос 82): показывать реестровое имя раскладки вместо идентификатора отклонено — путь к нему лежит через недокументированное соответствие `HKL` → `KLID`.

**Примечание к FR-92 (окно выше экрана).** Единица вёрстки диалога следует шрифту, а шрифт — масштабу экрана, поэтому окна программы тем выше, чем крупнее масштаб: окно настроек в 380 единиц шрифтом 10 pt — это около 847 точек при 100 % и около 1140 при 125 %. **Главный механизм — шаг шрифта по экрану** (вопрос 143): перед созданием каждого окна программа берёт самый крупный целый шаг шрифта шаблона — 10, 9, 8, 7 или 6 pt, — при котором самое высокое окно программы **на лице этого шага** помещается в рабочую область монитора, на котором окно откроется, с запасом 12 точек сверху и снизу; не крупнее 10 pt и не мельче лица 11 точек; шаг один на все окна одного монитора, и ключ к нему — экран, а не процент масштаба (на 1920 × 1080: 100 % — 10 pt, 125 % — 8 pt, 150 % — 7 pt; на 2560 × 1440 при 125 % — 10 pt). Всё, что рисует сама программа, — рамки, скругления, отступы, шаг строк, логотип, значки своих элементов — идёт по тому же шагу; полоса прокрутки, заголовок окна, меню и значок трея остаются на настоящем масштабе. Окно, выросшее по своему содержимому («От автора», «Последние письма»), если там, где его поставила система, оно не оставляет запаса 12 точек, ставится по центру рабочей области. **Последнее средство — прежнее**: если окно настроек не помещается и на самом мелком шаге, оно укорачивается до рабочей области и получает вертикальную прокрутку — содержимое движется колесом, полосой и клавишей `Tab` (фокус, ушедший за нижний край, подтягивает содержимое к себе). Саму вёрстку ради этого не уменьшают — уменьшается шаг шрифта, и вёрстка в единицах диалога идёт за ним сама. Смена масштаба на лету и перенос окна на монитор с другим масштабом не учитываются: шаг считается при создании окна.

**FR-92а. Тема оформления окон.** Всё видимое глазом — диалог настроек FR-92, контекстное меню трея FR-91, окно «О программе» — оформляется в одной из двух палитр: светлой («Туман») либо тёмной («Графит»); значения цветов — константы модуля `theme`, единственного владельца палитр. Настройка `[general].theme` принимает три значения: `system` (по умолчанию) — палитра выбирается по системной настройке приложений (значение `AppsUseLightTheme` раздела `HKCU\Software\Microsoft\Windows\CurrentVersion\Themes\Personalize`; отсутствие значения читается как светлая тема), `light` и `dark` — палитра фиксирована и от системы не зависит. При `theme = "system"` смена системной темы применяется к открытым окнам без перезапуска программы. Способ реализации — собственная отрисовка стандартных элементов документированными средствами (`WM_CTLCOLOR*`, `BS_OWNERDRAW`, `CBS_OWNERDRAWFIXED`, `MF_OWNERDRAW`, `LVM_SETBKCOLOR` и родственные, `DwmSetWindowAttribute`). Недокументированные механизмы — экспорты `uxtheme.dll` по ординалам (`SetPreferredAppMode` и соседние), именованные тёмные темы (`DarkMode_Explorer`, `DarkMode_CFD`) — не используются ни при каком условии: программа не опирается на то, что Microsoft вправе изменить между сборками Windows. Принятая цена решения перечислена в §10.

**Примечание к FR-92а (окно «О программе»).** Окно несёт имя программы, номер версии из ресурса `VERSIONINFO`, две строки описания и раздел **«Как пользоваться»** — панель в стиле разделов диалога с пятью пронумерованными строками: перекодировать набранное слово, вернуть исходный текст повторным нажатием, конвертировать выделение, найти паузу и настройки в значке трея, сменить клавишу в настройках. **Имя горячей клавиши в этих строках подставляется из настроек** (`[hotkey] key`), а не пишется в тексте: имя, которого сборка не знает, показывается как действующее по умолчанию. Решение пользователя, вопрос 82. Щелчок по имени программы открывает оболочкой её страницу на сайте автора — адрес вшит в сборку, имя в покое не отличается от надписи и получает подложку под курсором (решение 139.2), причём эта верхняя часть окна — значок, имя, строка версии и две строки описания — **общая с окном «От автора» FR-103** и во втором окне ведёт себя точно так же (решение 142.2).

**FR-93.** Автозапуск реализуется записью в `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`. Приложение с `uiAccess` запускается у обычного пользователя **без запроса UAC**, поэтому дополнительных механизмов не требуется.

**Примечание к FR-94 (подача захвата клавиши).** Пока захват взведён, поле **не редактируется**: ни каретки, ни выделения — вводить в него нечего, клавишу в нём ловят. Поле показывает приглашение приглушённым цветом, рамка поля меняется на цвет активного контура, кнопка «Задать» становится «Отмена», под полем стоит строка о выходе. Захват отменяют `Esc`, щелчок мимо поля и кнопки, и потеря окном фокуса; отмена возвращает прежнее имя клавиши. Отказ захват не гасит: программа показывает причину, отмечает отказ в журнале §4.10 (событие и счётчик в дампе) и ждёт следующего нажатия. Текстовая клавиша — такой же отказ (предупреждение о том, что при активной программе она перестанет вводить символ), и это единственное, что изменилось в классе отказов: назначить текстовую клавишу по-прежнему можно, но только правкой `[hotkey] key` в файле, и FR-95 к ней применяется без изменений. Решение пользователя, вопрос 82. Вне захвата поле клавиши не принимает фокус мышью и клавишей: каретки и выделения в нём не бывает; единственный вход в захват — «Задать».

**FR-95.** Горячая клавиша подавляется всегда, когда программа активна, независимо от наличия данных для конвертации, — **кроме процессов из списка исключений FR-84**, где она достаётся приложению. Обоснование подавления: решение принимается синхронно в хуке, тогда как наличие выделения устанавливается только после обращения к буферу обмена. Клавиша `Pause/Break` в современных приложениях практически не задействована; приложению, которому она нужна, её возвращает список исключений.

⚠ **Окно гонки.** Вердикт исключения вычисляется наблюдателем и приходит к потоку ввода через десятки миллисекунд после смены фокуса. Нажатие, сделанное в это окно, ещё подавляется и получает третий звук FR-100 — отказ. Окно ограничено бюджетом проверки поля и объявлено в §10.

### 4.11. Безопасность отладочной сборки

Требования этого раздела защищают разработчика: неисправный низкоуровневый хук способен поглотить весь клавиатурный ввод в системе, лишив возможности переключиться на другое окно и завершить процесс.

**FR-96. Аварийная комбинация.** `Ctrl+Alt+Shift+F12` обрабатывается **первой**, до любой другой логики callback хука, и выполняет немедленное снятие всех хуков и завершение процесса. Присутствует в обеих конфигурациях сборки. Комбинация подавляется.

**FR-97. Таймаут отладочной сборки.** Debug-сборка автоматически снимает хуки и завершается через заданное время с момента запуска (по умолчанию 10 минут). Значение задаётся переменной окружения `LANGSW_DEBUG_TIMEOUT_SEC`. В Release-сборке механизм отсутствует.

**FR-98. Снятие хуков при панике.** Устанавливается `std::panic::set_hook`, снимающий все хуки до аварийного завершения. Требование действует несмотря на `panic = "abort"`: обработчик паники вызывается до прерывания процесса.

**FR-99. Отказоустойчивый режим callback.** При возникновении паники внутри callback хука более трёх раз подряд буферизация отключается, а весь ввод пропускается без обработки. Программа остаётся запущенной и сигнализирует состояние иконкой в трее.

**FR-100. Звуковой отклик срабатывания.** По нажатию горячей клавиши программа издаёт звук — **один из трёх**, по исходу нажатия:

| исход | звук |
|---|---|
| замена выполнена | двойной щелчок |
| нажатие холостое — заменять было нечего, направление не определено, вердикт проверки поля ещё не получен | одиночный щелчок того же механизма |
| **программа отказала: поле пароля (FR-70)** | одиночный щелчок того же механизма **с низким телом под ним** — глухой стук |

Все три — один и тот же щелчок: два разных шума были бы двумя разными предметами, а один выключатель, щёлкающий дважды, раз или глухо, — один предмет, говорящий три вещи. Состояние «вердикт ещё не получен» третьему звуку **не подчиняется**: это незнание, а не запрет. Звук собственный, а не системный, и вшит в исполняемый файл: на диске звуковых файлов нет, внешних ресурсов не требуется. Механизм воспроизведения — `PlaySoundW` с флагами `SND_MEMORY | SND_ASYNC | SND_NODEFAULT`; путь ввода не задерживается — вызов выполняется на UI-потоке после исхода. Отключается настройкой `[feedback] sound` — одной на все три звука; по умолчанию включён. Обоснование третьего звука, слова пользователя 2026-09-09: «в поле пароля когда вводишь, нет никакого звукового сигнала и том что смена не удалась, да и в принципе сознательно не сработала».

Тем же третьим звуком отвечает **окно**, когда отказывает руке: девятая отмеченная раскладка в списке цикла окна настроек не встаёт — в дело идут первые `MAX_CYCLE` = 8 записей (§7), — и отказ слышен. Звук здесь добавка, а не всё лечение: при `[feedback] sound = false` он молчит, а галочка всё равно не встаёт, иначе отказ был бы невидим половине пользователей.

**FR-101. Письма от автора.** Пять писем, каждое показывается не более одного раза на повод: «Привет» — первый запуск, файла конфигурации нет; «Спасибо» — через 30 дней от первого запуска, одна отсрочка на 7 дней; «Что нового» — с решения 118.5 не показывается: описание изменений приходит с сигналом ленты до установки; `last_seen_version` подводится к версии сборки на каждом старте без письма; письмо и его тексты сохранены; «Обновление» — в ленте FR-102 версия новее установленной, один раз на версию, до обновления в меню трея стоит пункт «Доступна версия X…»; «Новость» — запись ленты типа `news` с непрочитанным номером. «Новость» считается прочитанной только по кнопке «Прочитано»; иначе показывается повторно через 7 и через 14 дней после первого показа, после чего до прочтения остаются только отметка на значке (FR-90) и пункт «Непрочитанное письмо…» в меню трея. Общие правила: окна немодальные, фокус не отбирают; кроме «Привета», письмо сначала объявляется уведомлением значка (`NIF_INFO`) и открывается по щелчку либо само, если уведомление не замечено, в спокойный момент — система не сообщает состояние «занят», нет полноэкранного приложения и презентации, клавиатура молчит не менее 30 с; не более одного письма в сутки. Тексты «Привета», «Спасибо» и «Что нового» — в строковых таблицах FR-94; тексты «Обновления» и «Новости» — из ленты. Программа хранит и показывает не более трёх последних новостей по номеру и одну, последнюю, запись об обновлении: старшие новости выбывают при чтении ленты, даже непрочитанные, их напоминания прекращаются, а отметка на значке ставится только за непрочитанные из трёх. Окно «Последние письма», доступное из «От автора», показывает эти три и письмо об обновлении, пока версия ленты новее установленной. Даты в письмах, в «Последних письмах» и в строках состояния окна «От автора» печатаются по григорианскому календарю при любой локали; имена месяцев и цифры — по локали интерфейса.

**FR-102. Лента автора.** Один файл TOML по адресам, вшитым в сборку, читаемый не чаще раза в 15 дней (первое чтение при первом запуске) на отдельном потоке штатным WinHTTP. Неудачное чтение (хост не ответил, код не 200, подпись или разбор не прошли) повторяется не раньше следующего календарного дня; день попытки, удачной или нет, хранится в `[letters] feed_last_try` и записывается до старта чтения (решения 148.8, 148.9). Запрос не несёт параметров, идентификаторов, версии и иных сведений о машине. Ответ ограничен 256 КБ. Тело файла подписано ключом автора (ECDSA P-256); подпись проверяется штатной криптографией Windows (CNG) по одному из двух открытых ключей из сборки — рабочему и запасному; файл с неверной или отсутствующей подписью, а также не разбираемый, отбрасывается без следа в интерфейсе, только с записью в журнал §4.10. Записи: `id`, `type ∈ {update, news}`, `date`, `title`, `text`, `link`; для `update` ещё `version`; `title` и `text` даны в подтаблицах по кодам языков §7 — `ru`, `en`, `uk`, `de`, `fr`, `es`, `pt`, `it`, `pl`, `cs`, `tr`, `el`, `he`, `ar`; обязательны `ru` и `en`, остальные по возможности; текст на иврите и арабском рисуется по правилам RTL Э30 (порядок чтения у DC, островки для латиницы и цифр версии); показывается язык интерфейса `[general] language`, при его отсутствии в записи английский, затем русский. Язык в запросе не передаётся: файл несёт все языки, выбор делается на машине. Из ленты берутся одна запись `update` и три записи `news` с наибольшими `id`, остальное игнорируется. Скрипт подписи `tools\sign-news.ps1` отказывается подписывать файл, где больше трёх новостей, больше одной записи об обновлении, нет обязательных полей, у записи нет русского или английского текста или размер превышает 192 КБ. Программа ничего не отправляет, не скачивает и не запускает; ссылки открываются оболочкой по щелчку. Чтение отключается настройкой `[letters] feed`, по умолчанию включённой. Выключатель в окне «От автора» появляется после первого показанного письма из ленты, но не раньше 90 дней от первого запуска; до того настройка правится в файле, как метод замены и тайминги (примечание к FR-92), и панель говорит об этом строкой. Факт и период чтения объявлены в окне «От автора» с первого дня и в README.

**FR-103. Окно «От автора».** Немодальное окно с панелями «Автор», «Новости и обновления», «Обратная связь»: ссылки на страницу поддержки и канал, сведения о ленте и её состояние, установленная и доступная версии, вход в мастер FR-104. Вход: пункт меню трея, кнопка в окне «О программе», ссылка в разделе «Диагностика» окна настроек. Верхняя часть окна — значок, имя, строка версии и две строки описания — **общая с окном «О программе» FR-92а**: то же содержимое, та же вёрстка, тот же щелчок по имени, открывающий страницу программы; подписи автора эта строка не несёт (решение 142.2).

**FR-104. Мастер «Написать автору».** Пять шагов для ошибки, три для пожелания. Собирает по галочкам: версию программы, сборку Windows из реестра, масштаб и число мониторов, раскладки, настройки, журнал из памяти; имя процесса и класс активного окна по отсчёту, без заголовка окна. Показывает полный текст перед отправкой. Исход: буфер обмена и ссылка через оболочку либо файл в папке журнала. Программа ничего не передаёт. Последний шаг мастера — благодарность в том же окне: капс «Готово», заголовок и текст по типу обращения, кнопка «Открыть канал» и «Закрыть».

Разделение обязательно: залипание потока UI на несколько секунд приведёт к молчаливому снятию хука системой (FR-80).

Поток ленты живёт ровно один запрос: он рождается по расписанию FR-102, читает, проверяет подпись, кладёт исход в почтовый ящик (§6.3) и завершается. Между чтениями его нет, и второй такой поток не создаётся, пока не завершился первый.

### 6.3. Синхронизация состояния

Буфер набора записывается исключительно потоком ввода. Читается — потоком ввода при конвертации. Кэш раскладок пишется потоком ввода при перестроении, читается им же. Флаг «поле пароля» пишется потоком наблюдения, читается потоком ввода — `AtomicBool` с упорядочением `Relaxed`. Конфигурация публикуется потоком UI через `arc_swap`-подобный механизм на базе `Atomic` указателя либо через `PostMessage` в поток ввода. **Мьютексы в пути хука запрещены** (NFR-04).

Третий механизм — **seqlock** по канону Boehm (*"Can seqlocks get along with programming language memory models?"*, MSPC 2012): счётчик поколения нечётен на время записи и чётен между записями, читатель берёт поколение до и после чтения и повторяет попытку при нечётном или изменившемся значении. Он применяется там, где поток ввода читает **составное** состояние, опубликованное другим потоком и обязанное быть согласованным целиком, — то есть там, где россыпь независимых атомиков допускала бы «рваное» чтение: список исключений `guard` (FR-84), словарь `diag` и пара либо цикл раскладок `layouts` (FR-31). Пишущего seqlock не блокирует, читателя не заставляет ждать владельца и мьютекса не требует, поэтому он совместим с NFR-04 и с бюджетом NFR-02. **Ни один читатель не ждёт неограниченно:** `layouts` и `guard` повторяют чтение ограниченное число раз и при исчерпании попыток возвращают определённый исход, `diag` не повторяет вовсе и пропускает запись, перезаписанную под ним. Неограниченный повтор был бы ожиданием под другим именем, а ожидание в пути хука запрещает NFR-04.

Четвёртый механизм — **почтовый ящик** ленты (FR-102). Поток ленты кладёт в статический ящик под мьютексом уже разобранный и проверенный подписью исход и посылает UI-потоку `PostMessage` с сообщением, **не несущим данных**: оно говорит только «загляни в ящик». Данные берутся и проверяются в ящике, а не в сообщении, — это прямое следствие SEC-05: подделанное сообщение того же кода приводит лишь к взгляду в пустой ящик. Мьютекс здесь допустим: он не лежит в пути хука (NFR-04), а оба его владельца — поток ленты и поток UI — созданы самой программой.

## 7. Схема конфигурации

Расположение: `%APPDATA%\Lang_Switcher\config.toml`
Каталог программы (`%ProgramFiles%`) недоступен на запись обычному пользователю — конфигурация в нём не хранится.

```toml
schema_version = 6

[general]
enabled   = true
autostart = true              # умолчание true. FR-93: при каждом старте установленная
                              # сборка приводит HKCU\Software\Microsoft\Windows\CurrentVersion\Run
                              # в соответствие с этим полем — если файла ещё нет либо он разобран
                              # и запись в него разрешена; иначе ключ при старте не трогается
language  = "ru"              # ru | en | uk | de | fr | es | pt | it | pl | cs | tr | el | he | ar
                              # Умолчание ПЕРВОГО запуска (файла ещё нет) — язык интерфейса
                              # Windows: первичный тег из GetUserPreferredUILanguages
                              # (de-AT → de, pt-PT → pt), первый из списка, который у нас
                              # есть; если ни одного — "en". Существующий файл не трогается:
                              # в нём отсутствующий language по-прежнему даёт "ru".
theme     = "system"          # system | light | dark

[hotkey]
key = "Pause"                 # имя виртуальной клавиши

[layouts]
mode        = "pair"          # pair | cycle
pair_source = "0x00000409"    # en-US
pair_target = "0x00000419"    # ru-RU
cycle       = ["0x00000409", "0x00000419"]  # в дело идут первые 8 записей, лишние отбрасываются молча

[replacement]
method               = "auto"        # auto | backspace | selection (auto — FR-42а)
inter_event_delay_ms = 0

[selection]
enabled                    = true
clipboard_timeout_ms       = 300
clipboard_restore_delay_ms = 200  # потолок 5000 мс; больше действует как 5000

[buffer]
capacity = 256                # 1…4096; 0 читается как 256, больше 4096 — как 4096, молча
idle_timeout_s = 300          # 0 — выключено; FR-15; иначе 30…86400, вне границ подтягивается молча

[exclusions]
processes = []

[feedback]
sound = true                  # FR-100

[diagnostics]
log_enabled = false

[letters]
feed               = true          # FR-102, правится только здесь
first_run          = 2026-09-02    # дата первого запуска
welcome_shown      = true
thanks             = "pending"     # pending | snoozed | done
thanks_due         = 2026-10-02
last_seen_version  = "0.38.0"       # виденная версия; «Что нового» не показывается (118.5)
last_letter        = 2026-10-02    # день последнего показанного письма: «не более одного в сутки»
feed_last_read     = 2026-09-02
feed_last_try      = 2026-09-02    # день последней попытки чтения, удачной или нет; повтор при отказе — не раньше следующего дня (148.8)
first_feed_letter  = 2026-10-14    # первое письмо из ленты; выключатель после него, не раньше 90 дней
latest_known       = "0.39.0"       # «Обновление», пункт меню
read_ids           = [12]          # прочитанные из трёх последних новостей
reminders          = { 13 = 1 }    # напоминания, только для трёх последних
first_shown        = { 13 = 2026-11-02 }  # день первого показа новости, от него считаются 7 и 14
```

**`schema_version` при добавлении `idle_timeout_s` не поднималась и остаётся `6`.** В модуле настроек нет `deny_unknown_fields`, поэтому файл, написанный новой сборкой, читается прежней без возражений — незнакомый ключ она просто игнорирует. Подъём до `7` дал бы обратное: при откате на предыдущую сборку тот же файл попал бы в карантин «из будущего» и не сохранялся бы до конца сессии. Отсутствующий ключ имеет определённое значение — умолчание раздела 7, — и мигрировать в таком файле нечего.

Миграция 5 → 6: `first_run` — день миграции, `welcome_shown = true`, `last_seen_version` пустая (до решения 118.5 — чтобы обновившиеся увидели «Что нового»; теперь её подводит к версии сборки первый же старт).

Неизвестные поля игнорируются, отсутствующие заполняются значениями по умолчанию. Пять числовых полей — `replacement.inter_event_delay_ms`, `selection.clipboard_timeout_ms`, `selection.clipboard_restore_delay_ms`, `buffer.capacity`, `buffer.idle_timeout_s` — мягкие. Значение, не являющееся целым числом, которое поле вмещает (`-1`, `1.5`, `"300"`), и синтаксическая опечатка в строке такого ключа внутри своего раздела (`300ms`, `3 00`, `5 min`) стоят только этого поля: оно получает умолчание, в диагностический журнал уходит строка, остальные настройки читаются как обычно, а чтение файл не переписывает. Закрытые множества (`language`, `mode`, `method`) и `schema_version` мягкими не бывают: ошибка в них, как и опечатка вне строки мягкого ключа, по-прежнему делает файл повреждённым целиком (§10, строка 12). При росте `schema_version` выполняется миграция. Сохранение печатает файл начисто из памяти программы: комментарии, порядок строк и незнакомые программе поля запись не переживают. Файл без `schema_version` (или со значением меньше 2) считается написанным программой и проходит миграцию — в том числе `method = "backspace"` → `auto`; вписанный руками `backspace` при этом теряется.

## 8. Права доступа и установка

### 8.1. Механизм uiAccess

Непривилегированный LL-хук **не получает** нажатия, когда в фокусе окно процесса более высокого уровня целостности (UIPI). Решение — манифест с `uiAccess="true"`.

```xml
<requestedExecutionLevel level="asInvoker" uiAccess="true" />
```

Права администратора **не выдаются**: в токен добавляется разрешение обходить UIPI при установке глобальных хуков и вызовах `SendInput`, и только оно. Уровень целостности при этом **измерен на подписанной сборке (T-09-2, перепроверено контролером): `0x3000`, High, при `Elevated = 0`** — то есть процесс поднимается выше среднего уровня, оставаясь непривилегированным. Это тот же механизм, которым пользуются экранная клавиатура, экранная лупа и экранный диктор.

### 8.2. Обязательные условия работы uiAccess

1. Исполняемый файл подписан Authenticode сертификатом, которому доверяет локальная машина.
2. Файл расположен в `%ProgramFiles%` либо `%SystemRoot%\System32` (каталоги, недоступные на запись обычному пользователю).

Отказы Windows при невыполнении условий **измерены**, и это три разных исхода при трёх разных условиях — смешивать их нельзя (урок вопроса 155):

* **подписи машина не доверяет (или подписи нет), запуск через `ShellExecute`** — программа не запускается вовсе: ошибка `8235 (ERROR_DS_REFERRAL)`, «Сервер возвратил ссылку». Измерено: неподписанный образ вне `%ProgramFiles%` — T-03-1; образ с подписью автора в `%ProgramFiles%` на машине, где сертификата автора нет, — проверка владельца на чистой машине 2026-10-03 (решение 155в);
* **`CreateProcess`** — ошибка `740 (ERROR_ELEVATION_REQUIRED)` **в любом расположении и при любой подписи**, в том числе доверенной и в `%ProgramFiles%`: флаг `uiAccess` в маркер ставит служба AppInfo, а до неё доходит только `ShellExecute` (T-09-2; окно установщика 0.90.0 «CreateProcess failed; code 740», 155в). **Расположение этим способом не проверяется вовсе**, и прибором различения он служить не может;
* **доверенная подпись, файл вне `%ProgramFiles%`, запуск через `ShellExecute`** — программа **запускается** с `UIAccess = 0`, то есть без полномочий обхода UIPI; тот же файл в `%ProgramFiles%` получает `UIAccess = 1` (T-09-2, один файл в двух расположениях).

Требование по существу остаётся прежним — без доверенной подписи и без `%ProgramFiles%` полномочий нет. Отсюда следует раздельная конфигурация сборок:

| Сборка | Манифест | Расположение | Назначение |
|---|---|---|---|
| **Debug** | без `uiAccess` | любое | Разработка и отладка. Покрывает все сценарии, кроме элевированных окон |
| **Release, полный образ** | `uiAccess="true"` | `%ProgramFiles%\Lang_Switcher` | Поставка: работает и в окнах программ, запущенных от имени администратора, где подпись доверена (§8.3) |
| **Release, запасной образ** | без `uiAccess` (`LANGSW_NO_UIACCESS=1`) | `%ProgramFiles%\Lang_Switcher` | Поставка там, где полному образу доверия нет: тот же код, запускается везде, окна администратора недоступны (§10, строка 41) |

### 8.3. Распространение и сертификат

**Свободное распространение, бесплатно.** Программа распространяется свободно и бесплатно — для личного пользования каждого скачавшего. Скачивание, установка и передача сборки другому человеку ничем не ограничены, платы и регистрации не требуется.

**Подпись — целевая модель: OV-сертификат.** Доверенный OV- (или EV-) сертификат от коммерческого удостоверяющего центра **планируется** и остаётся целевым состоянием: именно при нём условие 1 §8.2 выполняется на любой машине, а не только на машине разработчика. С июня 2023 по требованиям CA/B Forum закрытый ключ сертификатов подписи кода обязан храниться на аппаратном токене или в HSM.

**Подпись — состояние на сегодня: самоподписанный сертификат.** До приобретения OV сборки подписываются самоподписанным сертификатом автора `CN=Panda Koder`, создаваемым скриптом `tools/make-cert.ps1`: `New-SelfSignedCertificate` → установка в `Cert:\LocalMachine\Root` и `Cert:\LocalMachine\TrustedPublisher` → подпись `signtool` с названием программы и адресом её страницы. Требует прав администратора однократно. Такому сертификату доверяет **только та машина, на которой он установлен**, то есть машина разработчика.

**Что это значит на чужой машине — прямо.** Там, где сертификат автора в доверенные не установлен, условие 1 §8.2 не выполнено, и следствия такие:

1. запрос UAC при установке называет издателя неизвестным — измерено владельцем на чистой машине (155в). Предупреждение SmartScreen при скачивании установщика браузером — известное поведение Windows для файла без репутации; **нами не измерено**;
2. образ с `uiAccess` и подписью автора такая машина не запускает вовсе (§8.2, ошибка 8235). Поэтому установщик **сам**, без отдельного вопроса, создаёт на этой машине сертификат `CN=Lang Switcher for Windows (local)`, кладёт его публичную часть в `Cert:\LocalMachine\Root`, подписывает им полный образ и сразу уничтожает закрытый ключ (SEC-09), а затем ставит **полный** образ — тот, что работает и в окнах программ, запущенных от имени администратора. Где подпись автора на машине уже доверена, сертификат не создаётся;
3. если местный сертификат создать не удалось или установщик запущен с параметром `/NOLOCALCERT`, ставится **запасной** образ — тот же код без `uiAccess`: программа запускается и работает везде, кроме окон программ, запущенных от имени администратора (§10, строка 41).

Ограничение §8.5 при этом никуда не девается и не расширяется: защищённый рабочий стол недоступен и при доверенной подписи.

⚠ Обхода UIPI отсюда не появляется: §8.2 не ослабляется и не меняется ни на букву. Местный сертификат — штатный способ Windows дать доверие подписи на одной машине с согласия её администратора: установщик работает с правами администратора, полученными через запрос UAC. Тем же устройством пользуется AutoHotkey. Сертификат автора на чужую машину не ставится никогда.

### 8.4. Установщик

Inno Setup 6.x. Требования:
- установка в `%ProgramFiles%\Lang_Switcher` с однократной элевацией;
- **два образа одной сборки** (§8.2): файлом программы сначала становится запасной, полный заменяет его только после того, как его подпись на этой машине проверена как действительная — подпись автора, если машина ей доверяет, иначе подпись местного сертификата (§8.3, SEC-09); при любом сбое остаётся запасной образ, и установка не прерывается. Параметр `/NOLOCALCERT` — запасной образ без сертификата. Новой страницы и вопроса нет: одна строка на странице «Всё готово к установке» говорит, что сертификат будет создан;
- запуск программы после установки — через `ShellExecute` (флаг `shellexec`), а не `CreateProcess`: тот отказывает образу с `uiAccess` ошибкой 740 в любой папке (§8.2);
- корректное обновление поверх: завершение работающего экземпляра до замены файлов; местный сертификат прежней установки убирается до создания нового;
- регистрация автозапуска в `HKCU\...\Run`: ключ приводится в соответствие с настройкой `autostart` при каждом старте программы (FR-93), установщик его не пишет; выключается галочкой в настройках или пунктом меню трея «Запускать при входе в систему»;
- деинсталляция **без остатков, включая местный сертификат** в `Cert:\LocalMachine\Root`, и с удалением записи автозапуска; сертификат автора не трогается; конфигурация в `%APPDATA%` удаляется по подтверждению;
- язык мастера — по языку интерфейса Windows: тринадцать языков программы (официальные переводы Inno Setup и свои сообщения установщика в `installer\lang\`); греческой системе, для которой официального перевода нет, и всякой другой — английский;
- сам установщик подписан.

### 8.5. Неустранимое ограничение

**Ни uiAccess, ни любой другой механизм не работают на защищённом рабочем столе**: экран запроса UAC, `Ctrl+Alt+Del`, экран входа в систему. Доступ туда имеет только `winlogon`. Это ограничение операционной системы.

## 9. Безопасность и приватность

Программа по своей архитектуре перехватывает весь клавиатурный ввод и работает с расширенными правами на взаимодействие с интерфейсом. Требования ниже обязательны и не подлежат ослаблению.

**SEC-01.** Нажатия **никогда** не записываются на диск — ни в журнал, ни в конфигурацию, ни во временные файлы, ни в дампы аварийного завершения.

**SEC-02.** Буфер набора явно перезаписывается нулями при каждом сбросе, а не просто помечается пустым.

**SEC-03.** Сетевая активность ограничена одной операцией: чтением ленты автора по FR-102, не чаще раза в 15 дней (при отказе повтор не раньше следующего календарного дня), по HTTPS, штатным WinHTTP, с постоянных адресов из сборки. Запрос не несёт никаких сведений о машине и пользователе; ответ принимается только с действительной подписью автора и ограничен по размеру. Программа ничего не отправляет, не скачивает и не запускает. Операция отключается настройкой `[letters] feed`: в файле конфигурации с первого дня и выключателем окна «От автора» по FR-102; объявлена пользователю в окне «От автора» с первого дня и в README. В зависимостях не должно быть ни одного крейта с сетевыми возможностями — проверяется командой `cargo tree`; в Release-бинаре единственные сетевые адреса — адреса ленты, проверяется поиском по строкам бинаря.

**SEC-04.** Межпроцессное взаимодействие отсутствует: ни именованных каналов, ни сокетов, ни разделяемой памяти. Обоснование: процесс с uiAccess представляет повышенную ценность для атакующего, и любая точка входа расширяет поверхность атаки.

**SEC-04a. Единственное исключение — отладочный канал контроля.** Для автоматизации приёмочных проверок (§11.5) допускается именованный канал, отдающий состояние программы: длину буфера набора, флаг «поле пароля», позицию в цикле раскладок, счётчики отказов. Канал подчиняется жёстким условиям:

1. Компилируется **только** при включённой cargo-фиче `testing`, отсутствующей в конфигурации Release. Отсутствие символов канала в поставляемом бинаре проверяется автоматически (§13, критерий 8).
2. Отдаёт **только метаданные**. Содержимое буфера, коды клавиш и символы через канал не передаются ни при каких условиях — доступна лишь длина. ⚠ **Граница «только состояние» включает и величины, посчитанные из набранного слова, и они допускаются только поимённо.** Сегодня таких две: сколько среди единиц пакета замены было **различных** и совпал ли вставленный текст со стираемым. Ни символа, ни кода клавиши из них не восстановить, и обе нужны стенду, чтобы отличить «продукт построил схлопнутый пакет» от «приложение отобразило верный пакет схлопнутым». Правило: **у каждого ключа канала названо происхождение его значения**, и ключ, чьё значение выведено из текста, проходит только будучи назван в списке приёмки; прибор краснеет и на ключе без происхождения, и на производном ключе вне списка, и привязан к числу ключей, потому что молчаливый рост списка и был находкой.
3. Дескриптор безопасности разрешает подключение только владельцу текущего сеанса.
4. Работает исключительно на чтение. Команд, изменяющих поведение программы, канал не принимает.

Обоснование: без него требование SEC-06 недоказуемо автоматически. Содержимое поля пароля недоступно извне по устройству Windows, поэтому проверка «в поле пароля буфер не ведётся» методом чёрного ящика невозможна в принципе.

**SEC-05.** Скрытое окно программы игнорирует все сообщения, кроме явно обрабатываемых. Ни одно привилегированное действие не инициируется входящим оконным сообщением. Процессы того же уровня целостности способны отправлять сообщения нашему окну, и это учитывается. Сообщения темы и собственной отрисовки (FR-92а) — не исключение, а частный случай того же правила: `WM_SETTINGCHANGE` и `WM_THEMECHANGED` не несут привилегированного действия — реакция ограничена перечитыванием системной настройки и перерисовкой, содержимое сообщения дальше сверки строки `"ImmersiveColorSet"` не используется; `WM_DRAWITEM` и `WM_MEASUREITEM` обрабатываются только пока программа сама держит на экране меню либо диалог, которым эти сообщения адресованы, — подделанное сообщение вне этого окна времени игнорируется, а указатели из него за пределы сверки идентификатора и прямоугольника отрисовки не разыменовываются.

**SEC-06.** Ввод в полях пароля не буферизуется (§4.8).

**SEC-06a. Проверка поля пароля опирается на системную библиотеку, загружаемую внутрь процесса, и это признанная граница защиты.** Распознавание поля пароля (§4.8, уровень 3 FR-72) идёт через UI Automation, то есть через COM-сервер, который Windows загружает **в адресное пространство самой программы**. Путь к такому серверу Windows ищет в реестре, а `HKEY_CLASSES_ROOT` — это склейка ветки машины с веткой **пользователя**, куда пишет любая программа того же пользователя без прав администратора. Отсюда следствие, которое программа устранить не может: **на машине, где от имени пользователя уже работает вредоносная программа, Lang Switcher защищён не полностью** — подменив запись реестра, она получает свой код внутри процесса с `uiAccess`. Это не дефект реализации и не лечится настройкой: разделение потребовало бы выносить проверку пароля в отдельный процесс. Политика подписанных модулей (`ProcessSignaturePolicy`) намеренно **не** включается — она ломает сторонние надстройки, которыми пользуются люди.

**SEC-06b. Программа не запускает посторонние исполняемые файлы сама.** Открытие адреса или папки (кнопки «Открыть папку журнала», «Сохранить в папку журнала» мастера письма, ссылки писем и ленты FR-101 и FR-102) делается **единственной** функцией программы, и это правило для всех таких кнопок без исключения: вторая такая точка в коде запрещена и проверяется свипом приёмки. Что открывается, решает белый список — схема ровно `https://` и хост только из зашитых в сборку, — а всё прочее отвергается, и отказ пишется строкой журнала без самого адреса. ⚠ **Признанная граница:** открытие выполняется штатным для Windows способом, и если оболочка не работает либо на открытие папок назначен сторонний файловый менеджер, Windows создаёт **новый процесс, который наследует пропуск `uiAccess` этой программы**. Человек этого не заметит. Механизм остаётся прежним осознанно: способы попросить об открытии **уже работающую** оболочку в закреплённом составе зависимостей (§3.2, SEC-03) недостижимы, а менять состав ради этого решено не было.

**SEC-07.** Диагностический журнал, при включении, содержит только события программы (установка и снятие хука, ошибки переключения раскладки, отказы `SendInput`). Символы, коды клавиш и содержимое буфера обмена в журнал не попадают ни при каком уровне детализации.

**SEC-08.** Исходный код открыт, сборка воспроизводима. Это единственный практичный способ подтвердить выполнение SEC-01 и SEC-03 для внешнего пользователя.

**SEC-09. Местный сертификат установщика (§8.3) годен только на одно и живёт только пока нужен.** Он годен **только для подписи кода** (расширенное использование ключа — одно, подпись кода; использование ключа — только цифровая подпись) и **не является удостоверяющим центром** — выпустить им другой сертификат, в том числе сертификат сайта, нельзя. Закрытый ключ создаётся неэкспортируемым и **уничтожается сразу после подписи** полного образа; после установки подписать этим сертификатом что-либо ещё нельзя никому, и самому установщику тоже. Публичная часть лежит только в `Cert:\LocalMachine\Root` и в папке программы (`LangSwitcher-local.cer`); **удаление программы убирает сертификат**. Сеть при установке не используется: подпись ставится без метки времени, поэтому сертификат выпускается на 30 лет. Сертификат автора установщик не ставит и не трогает.

## 11. Тестирование

### 11.1. Модульные тесты

Модуль `convert` — чистая логика, покрытие обязательно:
- полный обход RU↔EN: все буквы обоих регистров, цифровой ряд с `Shift` и без, знаки препинания, `ё`/`~`;
- проверка соответствия по физической клавише: `Shift+2` → `@` ⇄ `"`;
- отсутствие отображения → символ сохраняется (FR-23);
- идемпотентность цикла: `N` конвертаций по кругу из `N` раскладок возвращают исходную последовательность побитово (FR-32);
- лигатуры (вывод `ToUnicodeEx` длиной больше единицы);
- мёртвые клавиши переносятся без изменений.

Модуль `layouts` — критерий «клавиша пишет хоть в одной раскладке кэша», на котором стоит граница пустого штриха FR-10: опрашивается каждая карта, ответ «да» даёт первая же; мёртвая клавиша FR-24 считается пишущей.

### 11.2. Интеграционные тесты

Тестовый стенд инжектирует синтетические события через `SendInput` (с отличной от рабочей сигнатурой `dwExtraInfo`) и проверяет состояние буфера. Покрываются все правила сброса из FR-10 — включая границу пустого штриха, `VK_PACKET` и роль семи клавиш громкости и медиа, — разрешение гонок FR-12, исключения FR-11 (все переключатели системного диалога) и таймаут покоя FR-15 вместе с его потолками и с тем, что схема конфигурации от него не поднялась.

### 11.5. Сквозной стенд приёмки

Отдельный исполняемый файл в `tests/e2e`, собираемый с фичей `testing`. Отвечает за все позиции матрицы, отмеченные **А**. Требования к нему:

1. Запускает целевое приложение, дожидается готовности его окна через UI Automation, а не по фиксированной задержке.
2. Инжектирует нажатия через `SendInput` с сигнатурой `dwExtraInfo`, **отличной** от рабочей, — иначе программа отфильтрует их как собственные.
3. Считывает результат через UI Automation (`ValuePattern` либо `TextPattern`), сверяет с ожидаемым и дополнительно проверяет активную раскладку окна.
4. Опрашивает отладочный канал SEC-04a там, где результат недоступен снаружи (позиция 14).
5. Восстанавливает исходное состояние системы после каждого сценария: закрывает запущенные приложения, возвращает раскладку, снимает временно подключённые раскладки, восстанавливает буфер обмена.
6. Выдаёт машиночитаемый отчёт: позиция, вердикт, фактическое значение, ожидаемое значение.
7. При аварийном завершении в середине прогона гарантированно снимает хук тестируемой программы — через её аварийную комбинацию (FR-96) либо принудительным завершением процесса.

### 11.6. Приёмочная сессия

Позиции, отмеченные **П**, требуют физического участия человека и **не блокируют разработку**. Они накапливаются и выполняются одним заходом в конце проекта.

Правила:
- Обнаружив позицию **П**, исполнитель не останавливается и не ждёт человека. Позиция помечается «отложена до приёмочной сессии», работа продолжается.
- К моменту сессии готовится сценарий: последовательность действий человека с точными формулировками, что именно наблюдать, и подготовленное окружение (запущенные приложения, установленная сборка).
- Ожидаемая длительность сессии — около 15 минут суммарно. Это **ориентир, а не ограничение**: позиция не переводится в **А** ценой риска или обхода защит стенда ради того, чтобы уложиться. Если измерение показывает, что автоматизация ненадёжна, позиция идёт в **П**, сколько бы их ни накопилось, а длительность приводится в сценарии честной цифрой.

Состав сессии — все позиции матрицы §11.3, отмеченные **П**, включая переведённые в **П** по итогам измерения: сноски 6 и 7 раздела 11.3 предусматривают такой перевод прямо, и он же возможен, когда окно позиции принадлежит процессу, которого стенд не запускал и потому трогать не вправе. К позициям добавляется субъективная оценка задержки ввода.

## 13. Критерии приёмки

Программа считается готовой при одновременном выполнении:

1. Все позиции матрицы §11.3 пройдены: помеченные **А** — стендом §11.5, помеченные **П** — в приёмочной сессии §11.6.
2. Все нефункциональные требования §5 подтверждены измерением, а не оценкой. Задержка callback хука измеряется `QueryPerformanceCounter` на выборке не менее 10 000 нажатий.
3. `cargo clippy -- -D warnings` без замечаний, `cargo test` зелёный.
4. `cargo tree` не содержит крейтов с сетевыми возможностями; поиск по строкам Release-бинаря находит из сетевых адресов только адреса ленты FR-102.
5. Каждый блок `unsafe` снабжён комментарием `// SAFETY:`.
6. Непрерывная работа 72 часа без роста памяти и без потери хука.
7. Установщик подписан, установка и удаление проходят без остатков — включая местный сертификат установщика (SEC-09), — обновление поверх работает.
8. В Release-бинаре отсутствуют следы отладочного канала SEC-04a **и переменных отладочных механизмов**: сборка выполнена без фичи `testing`, `Cargo.lock` и `cargo tree --features testing` сверены на отсутствие расхождений в составе зависимостей, а поиск по строкам бинаря — в UTF-8 и UTF-16LE — не находит ни имени именованного канала, ни имён операций этого канала в словаре журнала, ни переменных среды отладочных механизмов, включая переменную самозавершения FR-97 (`LANGSW_DEBUG_TIMEOUT_SEC`) и переменную подмены шага шрифта окон (`LANGSW_DEBUG_FONT_STEP`, вопрос 143). ⚠ У каждой искомой строки обязателен **положительный контроль** — сборка, в которой она обязана найтись; для строк фичи `testing` это сборка с фичей, для обеих переменных отладочных механизмов — сборка с включёнными `debug-assertions`, потому что они закрыты не фичей, а ими. Список строк и оба контроля — в `tools\verify-criterion8.ps1`.
